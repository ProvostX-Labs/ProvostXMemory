Getting Started

This guide walks through installing ProvostXMemory, wiring it into a host application, and selecting a vector index backend.

Requirements

  • .NET 8 (the library targets the .NET 8 SDK; any runtime compatible with .NET 8 works)
  • No native dependencies, no external services, no database server. Storage is files on disk; the vector engine is pure C#.

Install

The public package id is ProvostXMemory (packaging is owner-gated; until published, reference the projects directly):

dotnet add package ProvostXMemory

Hosts reference only the root package. Optional backend packages are added when a non-default index kind is selected:

PackageProvides
ProvostXMemoryFacade, abstractions, storage, lexical, fusion, chunking, graph, consolidation, correction, reranking, retrieval, eval, logging, telemetry, FlatJson backend
ProvostXMemory.VectorIndex.EngineOwn vector engine: FlatExact (SIMD), IVF, HNSW
ProvostXMemory.VectorIndex.GpuILGPU GPU kernels (Flat + IVF) with transparent CPU fallback

First run

using ProvostXMemory;
using ProvostXMemory.Abstractions;
using ProvostXMemory.Fusion;
using ProvostXMemory.Storage;
using ProvostXMemory.Telemetry;
using ProvostXMemory.VectorIndex.Engine;

var root = "/data/memory-root";
var layout = new MemoryRootLayout(root, "model-hash-v1");

IMemoryService memory = new MemoryServiceBuilder()
    .WithOptions(new MemoryServiceOptions(
        Storage: new StorageOptions(root),
        Vector: new VectorOptions("model-hash-v1", dim: 768, IndexKind.IndexKind.Hnsw),
        Graph: GraphOptions.Default,
        Fusion: new FusionOptions(),
        Consolidation: new ConsolidationOptions()))
    .WithStore(new JsonlMemoryStore(layout))
    .WithEmbedder(embedder)                       // host-injected IVectorEmbedder
    .WithIndexFactory(new EngineVectorIndexFactory())
    .WithFuser(new ReciprocalRankFuser())
    .WithTelemetry(NoopMemoryTelemetry.Instance)
    .Build();

Everything the host injects is an interface: IVectorEmbedder (your embedding model), IVectorIndexFactory (the backend), optionally IRetrievalGrader, IQueryRewriter, IReranker, IEntityExtractor, IMemoryTelemetry, and IMemoryLogSink. The library never picks models or calls out to the network on its own.

Write and read

var scope = new MemoryScope(MemoryScopeKind.Session, "user-42");

await memory.RememberAsync(new MemoryRecord(
    "note-1", scope, "helm-rollout", "Kubernetes rollout notes…",
    Category: "ops", Tags: new[] { "infra", "deploy" }));

await memory.BuildIndexesAsync(scope);

RetrievalResult result = await memory.RecallAsync(new RetrievalQuery(
    "kubernetes rollout",
    scope,
    TopK: 5,
    Filters: new RetrievalFilters(Tags: new[] { "deploy" })));

foreach (var hit in result.Records)
{
    Console.WriteLine($"{hit.Score:0.000} {hit.Record.Id}: {hit.Record.Key}");
}

Key semantics to know on day one:

  • BuildIndexesAsync(scope) must be called (or RebuildAsync() for all scopes) before recall returns results — index state is cold until built, and rebuilt deterministically after a restart.
  • Every record, query, and index artifact is bound to a MemoryScope. A query in one scope can never return records from another.

Dependency-injection wiring

MemoryServiceBuilder is a fluent convenience wrapper; underneath it is plain constructor injection, so it composes naturally with any DI container:

services.AddSingleton(sp =>
{
    var root = configuration["Memory:Root"]!;
    var layout = new MemoryRootLayout(root, configuration["Memory:ModelHash"]!);
    return new MemoryServiceBuilder()
        .WithOptions(new MemoryServiceOptions(
            Storage: new StorageOptions(root),
            Vector: new VectorOptions(
                configuration["Memory:ModelHash"]!,
                dim: 768,
                IndexKind.IndexKind.Hnsw),
            Graph: GraphOptions.Default,
            Fusion: new FusionOptions(),
            Consolidation: new ConsolidationOptions(),
            Logging: new MemoryLoggingOptions(
                Enabled: true,
                Level: MemoryLogLevel.Info,
                Sink: MemoryLogSinkKind.Injected,
                Integrity: MemoryLogIntegrity.HashChain)))
        .WithStore(new JsonlMemoryStore(layout))
        .WithEmbedder(sp.GetRequiredService<IVectorEmbedder>())
        .WithIndexFactory(new EngineVectorIndexFactory())
        .WithFuser(new ReciprocalRankFuser())
        .WithTelemetry(NoopMemoryTelemetry.Instance)
        .WithLogSink(sp.GetRequiredService<IMemoryLogSink>())
        .Build();
});
services.AddSingleton<IMemoryService>(sp => sp.GetRequiredService<MemoryServiceBuilder>().Build());

Register the embedder once; it is the single place where your embedding model enters the system. The model-hash in VectorOptions and MemoryRootLayout must match the model you inject — the library guards against dimension and model-hash mismatches when opening index artifacts (see Concepts).

Concepts

The memory model of ProvostXMemory: what a record is, how scopes isolate data, how representations and chunking work, and how the model-hash guard protects index consistency.

Records

A MemoryRecord is the atomic unit of memory. It is an immutable record type:

MemberDescription
IdStable identifier; unique within its scope.
ScopeThe MemoryScope this record belongs to (isolation boundary).
KeyShort symbolic name (also boosted in lexical scoring).
ContentPrimary text content.
CategoryOptional single-value classification, filterable.
TagsOptional label set, filterable; stored normalized (empty list, never null).
RepsAdditional MemoryRepresentation entries (multi-modal).
CreatedAt / UpdatedAtUTC timestamps, set on creation and maintained by the facade.
ExpiresAtOptional TTL deadline; honored by consolidation.
MetaFree-form string key/value metadata, persisted with the record.

Hosts create records; the facade owns index maintenance. RememberAsync, UpdateAsync, and ForgetAsync keep the dense and lexical indexes (and optionally the graph ledger) in sync through a per-record id ledger.

Scopes and the isolation model

A MemoryScope is (Kind, Id, ParentScope?) — hierarchical and immutable:

  • Kinds: Platform, Session, Tenant, Purpose, Custom.
  • Chain() flattens the parent chain, outermost first.
  • Contains(other) reports whether other is this scope or a descendant.

Isolation is structural, not conventional: every store, index, and graph operation is scope-bound, and scope resolution is enforced by MemoryRootLayout, which maps each scope to its own directory subtree. Cross-scope reads are impossible by construction — a query in scope A cannot observe records, vectors, or graph entities of scope B. This property is pinned by dedicated isolation tests in every layer and by end-to-end multi-tenant journey tests.

Parent chains are host-side metadata: they express intent (a session belonging to a tenant) and participate in Contains semantics, but persistence equality is by kind + id — scopes are stored under their own resolved paths regardless of parentage.

Representations

One record can carry multiple MemoryRepresentation entries with modality Text | Image | Table | Audio | Custom and an optional per-representation EmbeddingModelHash. This supports multi-modal memory: a table and its textual description can live on the same record and be embedded separately.

Retrieval addresses representations with vector ids of the form repr|<recordId>|<index>. The multi-representation retriever resolves these back to the owning record and reports the best-representation score per record, so one hit per record per stage regardless of how many representations matched.

Chunking

Long content is split into Chunk items before embedding. IChunker implementations:

  • StructuredChunker — respects document structure (line/paragraph boundaries) when ChunkOptions.RespectStructure is set.
  • SizeChunker — size/overlap-driven splitting.

ChunkOptions controls MaxChunkLength (default 512), Overlap, MinChunkLength, Separator, and structure respect; all combinations are validated (overlap must be smaller than the max length, minimum must not exceed the maximum, and so on). Chunk ids are encoded by ChunkIdCodec as scope-qualified identifiers and resolved back to their parent record by IParentResolver / ChunkParentResolver — the parent-document recall pattern: retrieve the best chunk, return the whole record.

Model-hash guard

Embedding models define the geometry of their vectors. Mixing vectors produced by different models (or dimensions) in one index silently destroys retrieval quality. ProvostXMemory prevents this at three levels:

  1. Path isolation — index artifacts live under vectors/<model-hash>/ inside each scope, so a different model means a different artifact set.
  2. Options guard — VectorOptions carries the model hash and dimension; index files record them at build time.
  3. Runtime guard — IVectorIndexGuard implementations reject opens with a mismatched model hash or dimension, throwing VectorIndexGuardMismatchException instead of returning garbage.

Consequence: swapping the embedding model is a data-migration decision, not a config flag. Re-embed and rebuild (RebuildAsync) under the new hash. See the FAQ.

Namespaces

The term *namespace* in this codebase means the scope-qualified partition that owns an artifact: a (scope, model-hash) pair for vectors, a scope for records/graph/lexical state. Query plans fan out across namespaces by targeting scope ids; fusion identifiers are scope-qualified so the same record id in two scopes never conflates (see Retrieval).

Scopes and Multi-Tenancy

Scopes are the isolation unit of ProvostXMemory. This page covers scope kinds, the on-disk layout, hierarchy semantics, and patterns for multi-tenant hosts.

Scope kinds

MemoryScopeKind has five values; they are labels for intent, not behavior switches:

KindTypical use
PlatformRoot scope of a host installation or product surface.
SessionOne conversation / working session.
TenantOne customer or organization in a multi-tenant host.
PurposeA functional partition (e.g. curated long-term notes vs. scratch).
CustomHost-defined partitioning.

Path layout

MemoryRootLayout resolves every scope to a unique directory subtree under the configured root:

<root>/
  manifest.json
  <scope-kind>/<scope-id>/
    records.jsonl
    chunks/
    vectors/<model-hash>/
      index.json          (FlatJson backend)
      index artifacts     (Engine / GPU backends)
    graph/
      entities.jsonl
      relations.jsonl
      clusters.jsonl

Because isolation is implemented as path resolution, cross-scope access is structurally impossible: an operation bound to scope Session/user-42 never reads or writes outside Session/user-42/. There is no "global override", and none is needed — see the multi-tenancy patterns below for legitimate cross-scope aggregation.

Hierarchy

MemoryScope is (Kind, Id, ParentScope?):

var tenant = new MemoryScope(MemoryScopeKind.Tenant, "acme");
var session = new MemoryScope(MemoryScopeKind.Session, "chat-1", tenant);

session.Chain();       // [Tenant/acme, Session/chat-1] — outermost first
tenant.Contains(session);   // true
session.Contains(tenant);   // false

Semantics pinned by tests: chains flatten outermost-first; Contains is reflexive and transitive over the chain; scopes are immutable (WithParent returns a copy). Persistence equality is kind + id — parent chains are host-side metadata used for Contains decisions and query-plan fan-out, and do not change where artifacts live.

Multi-tenancy patterns

Strict isolation (default). One scope per tenant; every RecallAsync and RememberAsync carries the tenant's scope. Nothing crosses. Use QueryPlan fan-out only when you deliberately want a merged view.

Scoped aggregation via plans. To answer a question "over a tenant and the current session", issue a RetrievalQuery with a QueryPlan whose steps target both scope ids. The plan runner fuses results with scope-qualified ids — the same record id in two scopes stays distinct — and structural isolation is preserved because fan-out is an explicit, declared operation, not ambient access.

Root + children. Model shared knowledge at the root (Platform) and per-context children beneath it (Tenant, Session). Children are separate scopes with their own artifacts; "inheritance" of knowledge is expressed as plan fan-out, not implicit reads.

Enumeration. IMemoryService.Scopes() lists existing scopes under the root (via the store's IScopesAware hook, with a directory-layout fallback), enabling admin-style overviews without breaching per-scope read isolation.

Testing your isolation story

The library's test suite pins cross-scope invisibility at the storage, retrieval, and journey levels. For host-side confidence, assert in your own tests that a query scoped to tenant A never returns tenant B record ids — RecallAsync makes this a data assertion, no configuration required.

Retrieval

How a query becomes an answer: the pipeline stages, when to use each retrieval route, and how filters apply.

Pipeline overview

                       RetrievalQuery (text, scope, topK, filters, plan?)
                                        |
                     ┌──────────────────┴──────────────────┐
                     |  MemoryService.RecallAsync routing  |
                     |  plan → corrective → hybrid → rerank|
                     └──────────────────┬──────────────────┘
                                        |
        ┌───────────────┬───────────────┴────────────────┐
        ▼               ▼                                ▼
   dense vector     lexical (BM25)                  query plan fan-out
   search per       search per scope                across target scopes
   scope            + key boost
        └───────┬───────┘
                ▼
        fusion (RRF, k=60 default; weighted dense/lexical)
                ▼
        resolve vector/chunk ids → memory records (parent-document recall)
                ▼
        filter enforcement (tags / category / date window)
                ▼
        optional rerank (IReranker)
                ▼
        corrective loop (when a grader is wired): grade → rewrite → retry
                ▼
        RetrievalResult + diagnostics (per-stage scores, timings)

Every stage is scope-exact. The scope index registry resolves the vector index, lexical index, and record provider for the query's scope; nothing from another scope enters the funnel.

Hybrid retrieval (default route)

HybridRetriever (implements IHybridRetriever) runs dense and lexical search in parallel for the query scope, then fuses:

  • Dense — the query is embedded with the host's IVectorEmbedder and searched against the scope's vector index.
  • Lexical — the tokenized query is scored against the scope's BM25 index (Bm25Scorer, saturated-TF IDF weighting plus a key-term boost).
  • Fusion — ReciprocalRankFuser combines the ranked lists with Reciprocal Rank Fusion (FusionOptions.RrfK, default 60) and configurable DenseWeight / LexicalWeight. Zero weights drop a stage entirely; a deterministic fallback ordering handles the all-zero edge case.
  • Resolve — vector ids (including repr|… multi-representation ids and chunk ids) resolve back to records via the per-record id ledger and parent resolver.
  • Rerank — if an IReranker is wired, candidates are re-scored after fusion.

Use this route when you want the standard quality/speed balance with no extra infrastructure.

Reranking

Three built-in IReranker implementations:

RerankerBehavior
NoopRerankerPass-through; default when none is wired.
ScoreBoostRerankerHeuristic boosts for tag matches, key-term hits, and category matches; length-based penalties (ScoreBoostRerankerOptions).
ClientBackedRerankerDelegates to an IRerankerClient (your cross-encoder/LLM service) with a fallback IReranker; ClientBackedRerankerOptions.TrustClientCompletely controls whether client order is taken verbatim or fused with the fallback.

The library stays LLM-agnostic: reranking intelligence is injected, never built in.

Corrective loop

CorrectiveRetriever (implements ICorrectiveRetriever) wraps the hybrid retriever with a self-checking loop:

  1. Retrieve candidates via the hybrid retriever.
  2. IRetrievalGrader grades each candidate Relevant | Irrelevant | Uncertain (host-injected — typically an LLM call).
  3. If evidence is weak (below CorrectionOptions.RelevanceFloor), IQueryRewriter (default KeywordQueryRewriter) rewrites the query and retries.
  4. If the result set is empty and UseFetcherOnEmpty is set, the injected IExternalFetcher is invoked — the extension hook for web augmentation. The library never fetches on its own.

Use this route when recall quality matters more than latency, and you have a grading signal available.

Graph retrieval

The graph layer stores entities and relations extracted from memory records (via IEntityExtractor — HeuristicEntityExtractor ships in-box; hosts may inject an LLM-backed extractor) into a scope-pinned JsonlMemoryGraphStore.

GraphRetriever (implements IGraphRetriever) maps a query to relevant entities, traverses Neighbors / ShortestPath, and returns records from the relevant subgraph together with GraphCluster summaries. Consolidation-emitted cluster summaries also surface in ordinary recall results as records with category summary and are linked as graph clusters.

Use graph retrieval when questions are relational ("who is connected to X", "what cluster does this belong to") rather than purely similarity-based.

Query plans

A QueryPlan is a declarative, ordered list of QueryPlanStep entries, each with an Action, TargetScopes (scope ids to fan out to), and TopK. QueryPlanRunner executes the steps:

  • Fan out retrieval across target scopes, with scope-qualified fusion ids so identical record ids in different scopes stay distinct.
  • Merge step results through the fuser.
  • One weak-evidence retry: if merged evidence is thin, the query is rewritten once (IQueryTextRewriter, default KeywordQueryTextRewriter) and re-executed.

Use a plan when one logical question spans multiple scopes (e.g. a session scope plus its tenant parent) or when the agentic surface should express retrieval as data. MemoryService.RecallAsync routes to the plan runner automatically when RetrievalQuery.Plan is set.

Filters

RetrievalFilters supports tag sets, a single category, and a date window (From / To). Filters are enforced after candidate resolution (RetrievalFilterApplier), not merely hinted — filtering is pinned by dedicated enforcement tests. Filter on tags/category/date when the candidate set should be narrowed semantically *and* structurally.

Diagnostics

RetrievalResult.Diagnostics exposes per-stage scores and timings; IMemoryTelemetry receives the same signals for host-side observability. Stage names are stable constants (StageNames).

Backends

Every vector index backend implements the same IVectorIndex contract and must pass the same conformance suite (build, add, remove, search, flush, dimension/count invariants). Switching backends is a configuration change: set VectorOptions.IndexKind and wire the matching IVectorIndexFactory.

The contract

MemberDescription
Build(items)Replaces index contents with the given VectorItem set.
Add(item) / Remove(id)Incremental mutation (where supported).
Search(vector, k)Returns ScoredVectorId list, best first.
Dim / CountDimension and current item count.
FlushPersists durable state.

Guards (IVectorIndexGuard) protect against dimension and model-hash mismatches; violations throw VectorIndexGuardMismatchException. Missing ids throw VectorIndexIdNotFoundException.

FlatJson (default, core package)

  • Mechanism: vectors held in a per-scope VectorNamespaceFile (transactional JSON file, written via AtomicFileWriter); search is brute-force cosine over the scope's items.
  • Complexity: build O(n·d); search O(n·d) per query.
  • When to choose: small scopes (up to a few thousand vectors), persistence-first deployments, environments where zero extra dependencies matter. It is also the parity baseline all other backends are tested against.
  • Persistence: JSON in the scope's vectors/<model-hash>/ directory; survives restarts without a rebuild.

FlatExact (own engine, SIMD)

  • Package: ProvostXMemory.VectorIndex.Engine.
  • Mechanism: exact brute-force search with Vector512 SIMD kernels (VectorMath, VectorScanner, VectorTopKBuffer); in-memory item store with configurable distance metric (Engine Options).
  • Complexity: build O(n·d); search O(n·d) but with a large SIMD constant-factor win over FlatJson.
  • When to choose: exactness required and up to ~10k vectors per scope; also the reference result source for cross-backend parity tests.

IVF (own engine)

  • Package: ProvostXMemory.VectorIndex.Engine.
  • Mechanism: k-means coarse quantizer (KMeansQuantizer, seeded and deterministic) partitions vectors into inverted posting lists; a query scans only the nearest nprobe lists. IvfPostingLists, IvfMember, KMeansResult are the supporting types.
  • Complexity: build O(iterations · n · d); search O(nprobe/ncentroids · n · d) — sublinear in n.
  • Trade-off: recall depends on nprobe; results are deterministic for a given seed and build order.
  • When to choose: 10k–1M vectors where a small, tunable recall loss buys large search-speed gains.

HNSW (own engine)

  • Package: ProvostXMemory.VectorIndex.Engine.
  • Mechanism: hierarchical navigable small-world graph — HnswBuilder constructs layered graphs (HnswGraph), level assignment is seeded (HnswLevelAssigner), search is greedy beam descent (HnswSearcher, HnswBeamSearcher).
  • Complexity: build O(n·log n·d); search approximately O(log n·d).
  • Patent-safe semantics: indexes are immutable after build; mutations trigger a batch rebuild. This deliberately avoids incremental dynamic-update methods (see the patent addendum in ARCHITECTURE.md).
  • Quality: measured recall@10 = 0.998 on a 2000×64 synthetic corpus; two identical builds produce bit-identical results (determinism pinned by tests).
  • When to choose: 10k–10M vectors with high recall requirements and read-mostly workloads.

GPU (ILGPU)

  • Package: ProvostXMemory.VectorIndex.Gpu.
  • Mechanism: own ILGPU kernels for exact flat scoring and IVF list scans (GpuVectorKernels, IlgpuScoreLauncher, GpuVectorMatrix). Kernels are one-thread-per-slot with chunked launches — no barriers or shared memory — so accumulation order is identical to CPU: results are bit-exact between GPU and fallback paths.
  • Availability: IGpuAccelerator discovery is lazy and exception-guarded (IGpuContextPolicy, GpuDiscoveryOptions). On machines without a compatible accelerator the index transparently delegates to an injected CPU IVectorIndex with identical results; the same conformance suite passes on CPU-only machines via this path.
  • Factories: GpuVectorIndexFactory wraps an EngineVectorIndexFactory for the fallback; the engine factory itself rejects IndexKind.Gpu by design (explicit routing, pinned by tests).
  • When to choose: Flat/IVF-sized workloads where an accelerator is present and batch scoring throughput matters.

Consolidation

Consolidation is the maintenance pass that keeps a scope's memory healthy: deduplication, TTL expiry, and cluster-summary emission. It is triggered explicitly via IMemoryService.ConsolidateAsync(scope, options) — the library never mutates memory in the background on its own.

What a pass does

MemoryConsolidator (implements IMemoryConsolidator) runs over one scope:

  1. Deduplication — ThresholdDedupDetector (implements IDedupDetector) finds near-duplicates by embedding similarity at or above ConsolidationOptions.DedupSimilarityThreshold. Survivors are the oldest record; the survivor's tags are the union of the duplicate set's tags; newer duplicates are removed and their index artifacts are cleaned up.
  2. TTL expiry — when ConsolidationOptions.ExpireTtl is set, records whose ExpiresAt is in the past are deleted; expiry persists across restarts.
  3. Cluster summaries — when ConsolidationOptions.EmitClusterSummaries is set, ClusterSummarizer (implements IClusterSummarizer) produces a new summary record for each coherent cluster:
  • the summary record is stored with category summary and appears in ordinary recall results;
  • the cluster is also recorded in the scope's graph store (IMemoryGraphStore cluster write path), linking the member entities.

The pass returns a report (via ConsolidationReportMeta) describing removals and emissions, and the facade refreshes or removes affected index artifacts so recall immediately reflects the consolidated state.

Options reference

OptionDefaultEffect
DedupSimilarityThresholdhigh (≈0.99999 used in journeys)Similarity at which two records are considered duplicates.
ExpireTtltrueDelete records past ExpiresAt during the pass.
EmitClusterSummariestrueGenerate summary records + graph clusters.

ConsolidationTuning exposes additional internal tuning knobs to the consolidator implementation.

Policies and recommended cadence

  • Threshold choice: set the dedup threshold as high as precision allows. At 0.99999+ only true restatements merge; lowering it aggressively risks collapsing distinct memories.
  • When to run: after bulk ingestion, periodically for long-lived session scopes, and before eval runs that should measure consolidated-state quality.
  • Ordering guarantees: consolidation is deterministic — the same store state and options produce the same survivors, unions, and summaries (pinned by tests, including non-regression of golden-query scores across a consolidation pass).
  • Index consistency: you do not need to rebuild after consolidation; the facade refreshes index artifacts as part of the pass. A full RebuildAsync remains available for wholesale reindexing.

Evaluation

The ProvostXMemory.Eval package measures retrieval quality with standard ranking metrics, guards against regressions, and produces JSON reports. It is the same harness used by the library's own journey tests (golden-query recall gate at Recall@5 ≥ 0.9, achieved 1.0).

Usage

var factory = new DefaultEvalServiceFactory(vectorDim: 768);
var runner = new EvalRunner(factory);

var caseSet = new EvalCaseSet("release-notes", new[]
{
    new EvalCase(
        CaseId: "q-01",
        Query: "kubernetes rollout",
        Scope: scope,
        RelevantIds: new[] { "note-1" },
        RelevantKeys: Array.Empty<string>())  // optional key hints
    // ...
});

EvalRunnerOptions options = new(
    TopK: 10,
    Thresholds: new EvalMetricThresholds(recallAtK: 0.9));

var report = await runner.EvaluateAsync(caseSet, options);

The EvalServiceFactory abstraction builds a self-contained service (store, embedder, indexes) per evaluation; DefaultEvalServiceFactory composes the standard stack, and DeterministicEvalCorpus generates reproducible synthetic corpora (ClusterHashEmbedder provides deterministic embeddings with a fixed noise amplitude). disposeRootDirectory controls cleanup of the temporary root.

Metrics

Let *R* be the set of relevant record ids for a case, *k* the cut-off, and *d(i)* the rank position of the *i*-th relevant result in the returned ranking.

MetricFormulaMeaning
Recall@k&#124;R ∩ top-k&#124; / &#124;R&#124;Fraction of relevant records found within the top *k*.
Precision@k&#124;R ∩ top-k&#124; / kFraction of the top *k* that is relevant.
MRR(1/&#124;R&#124;) · Σ 1/d(i)Mean of reciprocal ranks of the first relevant hit (1.0 when the first result is relevant).
NDCG@kDCG@k / IDCG@k, where DCG@k = Σ<sub>i≤k</sub> gain(i)/log<sub>2</sub>(i+1)Discounted cumulative gain normalized by the ideal ranking; supports graded gains from per-hit traces.

Metric math lives in EvalMetricMath (hand-verified against known answers, pinned by EvalMetricMathTests). Per-case results are EvalCaseMetrics; per-case hit traces (EvalCaseTrace, EvalCaseTraceHit) carry ids, scores, and gains.

Reports

EvalReportJson serializes a full report — aggregate metrics plus per-scope and per-stage breakdowns, threshold evaluations, and traces — in snake_case JSON. Round-trips are byte-identical (canonical rewrite), so reports diff cleanly in version control.

Regression guarding

EvalMetricThresholds declares per-metric floors:

new EvalMetricThresholds(recallAtK: 0.90, mrr: 0.8);

Violations are reported as MetricThresholdViolation entries (metric, actual, threshold) collected in MetricThresholdViolations. A non-empty violation list means the harness fails the run — wire it into CI as the recall-regression guard: fix the corpus and golden queries once, then any retrieval change that drops quality below the floors fails the build instead of shipping.

Recommended practice:

  1. Keep golden queries per scope in version control (the EvalCaseSet is plain data).
  2. Pin thresholds slightly below observed baselines so noise does not flap.
  3. Diff serialized reports after intentional changes to see exactly which cases regressed.

Logging and Audit Hash-Chain

ProvostXMemory ships a self-contained logging facility with an audit-grade integrity mode: append-only files, a SHA-256 hash chain for tamper evidence, rotation, retention, and strict content minimization.

Disabled by default

Logging is off by default with zero cost: no files are created, no allocations occur. Enable via MemoryServiceOptions.Logging:

Logging: new MemoryLoggingOptions(
    Enabled: true,
    Level: MemoryLogLevel.Info,
    Sink: MemoryLogSinkKind.File,          // File | Console | Injected
    Directory: Path.Combine(root, "logs"),
    FileNamePattern: "memory-{date}.log",
    Format: MemoryLogFormat.JsonLines,
    IncludeContent: false,                 // content NEVER logged by default
    Integrity: MemoryLogIntegrity.HashChain,
    RetentionDays: 30)

CategoryLevelMeaning

Each MemoryLogEntry carries a timestamp, monotonically increasing sequence number, level, category, optional MemoryLogScope (kind + id), correlation id, duration, and the chain fields.

The audit hash chain

When Integrity = MemoryLogIntegrity.HashChain, every entry is chained:

entryHash(n) = SHA-256( sequence(n) ‖ timestamp(n) ‖ level ‖ category ‖ payload ‖ previousHash )

HashChainAppender computes and appends the chain; previousHash of entry *n* is entryHash(n-1), so any modification, deletion, or reordering of historical entries breaks every subsequent link.

Verifying a log

LogChainVerifier walks a log file (or stream) from the beginning and returns a LogChainVerificationResult:

var verifier = new LogChainVerifier();
LogChainVerificationResult result = verifier.Verify(logFilePath);

if (!result.IsValid)
{
    // result.BrokenAtSequence: first sequence number where the chain broke
    // result.Detail: human-readable failure description
}

A valid result means the log is complete and unmodified from the first entry onward. This makes the log admissible as internal audit evidence: silent edits are detectable, and truncation is detectable as a chain break at the missing sequence.

Retention and rotation

  • RetentionSweeper deletes log files older than RetentionDays. Run it on your schedule (e.g. at service start) — retention is explicit, never implicit.
  • Rotation follows FileNamePattern; rolling behavior is pinned by tests (FileRollingTests).
  • Deleted log segments are not chains-compatible by design: if you must delete aged logs, delete whole files and treat each file as an independent chain (each file starts its own chain at sequence 0).

Routing into host logging

Use Sink: MemoryLogSinkKind.Injected plus MemoryServiceBuilder.WithLogSink(...) to forward MemoryLogEntry objects into your own logging pipeline. Note that hash-chain integrity applies to entries as emitted; if you need the chain, keep the file sink enabled as well.

FAQ

How does scope isolation actually work?

Isolation is structural. Every record, index, and graph artifact lives under its scope's resolved directory path (<root>/<scope-kind>/<scope-id>/…), every API operation is scope-bound, and query routing resolves indexes per scope through a scope-exact registry. A query in one scope has no code path that can read another scope's data. Cross-scope access happens only when you explicitly declare it via a QueryPlan fan-out. This is enforced at the storage, retrieval, and end-to-end levels by dedicated tests.

Can I swap the embedding model?

Yes, but it is a migration, not a toggle. Vectors are meaningless across models, so index artifacts are namespaced by model hash and guarded at open time (VectorIndexGuardMismatchException). To switch: configure a new model hash and dimension in VectorOptions and MemoryRootLayout, then re-embed and RebuildAsync(). Old artifacts under the previous hash remain on disk until you remove them. The library never downloads or selects models — the embedder is your injected IVectorEmbedder.

Does it need a server?

No. ProvostXMemory is an in-process library. Storage is transactional JSON/JSONL files under a root directory; the vector engine is pure C#. The only external integration points are the ones you inject (embedding model, optional grader/rewriter/reranker clients, optional external fetcher).

What are the GPU requirements?

None mandatory. The GPU layer (ProvostXMemory.VectorIndex.Gpu, shipped in the single ProvostXMemory package) uses ILGPU kernels for Flat and IVF search, with lazy, exception-guarded accelerator discovery. On CPU-only machines — or with no compatible accelerator — the index transparently falls back to an injected CPU implementation with bit-identical results (identical accumulation order by construction). Configuring GPU unconditionally is therefore safe; the same conformance suite passes on CPU-only machines via the fallback.

What is the persistence format?

Human-readable files: JSONL for records (records.jsonl), JSON for manifests and FlatJson vector namespaces, JSONL for graph entities/relations/clusters. All writes go through AtomicFileWriter (temp file + atomic swap, optional fsync). Engine indexes persist their own artifact formats under vectors/<model-hash>/. Old-format record files are read forward-compatibly (Reps/Meta additions are backward-compatible).

Is it thread-safe?

Public facade operations are asynchronous and safe to call concurrently. Index mutation follows a build-or-rebuild model (HNSW indexes are immutable after build; mutations trigger batch rebuilds), which avoids the classic concurrent-mutation hazards. For heavy concurrent write workloads, serialize writes per scope as you would any transactional file store. Conformance tests exercise the documented behaviors; treat per-index instances as not thread-safe for concurrent mutation.

How do I make recall results appear?

Call BuildIndexesAsync(scope) after remembering records — index state is intentionally cold until built, and a fresh service over an existing root restores indexes via BuildIndexesAsync/RebuildAsync. Rankings after a rebuild are identical to before (determinism is tested).

Which backend should I pick?

Start with the zero-dependency FlatJson default. Move to the engine's FlatExact for SIMD-speed exact search, IVF at 10k–1M vectors when you accept a tunable recall trade-off, and HNSW at 10k–10M vectors for high-recall approximate search (measured recall@10 = 0.998). See Backends.

Can I use my own reranker or grader?

Yes — that is the design. Implement IReranker (or IRerankerClient for an external rerank service), IRetrievalGrader, and IQueryRewriter, and inject them. The library is LLM-agnostic: it orchestrates the corrective loop but never owns a model.

How does consolidation decide what to delete?

Deduplication keeps the oldest record of a near-duplicate cluster and unions the tags onto the survivor; TTL expiry deletes records past ExpiresAt; cluster summaries are additive (new summary-category records plus graph clusters). All decisions are deterministic for a given store state and options. See Consolidation.

Does logging leak record content?

No. IncludeContent defaults to false, and when disabled, record content never appears in any log output — enforced by content-leak tests. Log entries carry scope identity, category, timings, and correlation ids, not memory content.

How do I verify logs have not been tampered with?

Enable MemoryLogIntegrity.HashChain and periodically run LogChainVerifier.Verify(path). Each entry's hash covers its sequence number, timestamp, category, payload, and the previous entry's hash, so edits, deletions, and reordering are all detectable. See Logging.

Can one record id exist in multiple scopes?

Yes — ids are unique per scope, not globally, and query plans handle collisions via scope-qualified fusion identifiers so identical ids never conflate across scopes.

What .NET version is required?

.NET 8. There are no native library requirements beyond the .NET runtime; the GPU package adds the ILGPU runtime only if you reference it.
